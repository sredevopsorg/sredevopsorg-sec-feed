# ADR-0006: Lock dependencies with pyproject.toml and uv.lock

- Status: Accepted (implemented)
- Date: 2026-10-17

## Context

The API previously listed six direct runtime pins in `requirements.txt` and
`pytest` in `requirements-dev.txt`. Nothing pinned transitive versions, so
Docker and CI resolved a different graph at every build. The local ignored
`.pip-packages` tree had already drifted from the declared pins (FastAPI
0.141.1 vs 0.143.0, psycopg 3.3.5 vs 3.3.6), which is exactly the kind of
drift a lockfile is meant to prevent. There was also no automated vulnerability
audit.

The application is not distributed as a Python package: Docker copies `app/`
and runs uvicorn. The dependency tooling must support that application-style
layout, multi-arch images, and a small contributor workflow.

## Decision

1. Declare direct dependencies and the `dev` dependency group in
   `pyproject.toml`. Keep deliberate exact pins for direct dependencies.
2. Set `[tool.uv] package = false` so uv treats the repository as an
   application and does not try to build/install it.
3. Commit `uv.lock`, generated by uv 0.13.1. The lock contains the complete
   graph with hashes for every supported platform.
4. Install with `uv sync --frozen` in Docker and CI. The API image uses a
   multi-stage build: install the lock into `/app/.venv` in a builder stage,
   then copy only the venv into the non-root runtime stage.
5. Verify the lock with `uv lock --check` and installed consistency with
   `uv pip check`.
6. Audit the runtime graph in CI with `pip-audit`; dev-only advisories are
   informational.
7. Let Renovate update `pyproject.toml` + `uv.lock` together and enable
   lock-file maintenance for transitive refreshes.

## Consequences

- Docker, CI, and host development install the same hash-verified graph.
- A stale lock fails CI instead of silently resolving newer transitives.
- Contributors need uv 0.13.1+; `requirements*.txt` is removed to avoid a
  second source of truth.
- The runtime image contains only the virtualenv, not uv or build caches.
- Multi-arch builds remain possible because the lock carries platform-specific
  wheel hashes and the image is built per platform.
- A new runtime advisory can fail CI; triage and update rather than ignoring it.

## Alternatives considered

- **pip-tools compiled requirements.** Viable and familiar, but it would keep a
  separate requirements-file workflow and add pip-tools to the dev toolchain.
  uv provides the same hash-locked result with a single committed lock and
  first-class Renovate support.
- **`pip freeze` lock without hashes.** Simpler, but it does not verify
  artifact integrity and still needs a second file.
- **No lockfile.** Rejected: it is the current failure mode (transitive drift,
  no audit baseline).
- **Install the app as a package.** Rejected: this is a deployed application,
  not a library; `package = false` keeps the image and test workflow simple.
